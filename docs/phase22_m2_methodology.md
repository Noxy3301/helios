# Phase 22 — Cost-constant methodology & M2 calibration plan

_Answers "is per-SF hardcoding wrong / what is the basis / should it be dynamic", grounded in the literature (workflow wf_e3731efc-06b, 9 agents; grounded reviewer GO, all in-repo citations verified; Codex review blocked only by sandbox, no substantive defect)._

## Verdict: per-SF hardcoding is NOT wrong (scale-invariant in kind), but 8.0 is provisional

NOT WRONG — scale-invariant IN KIND, but the specific value 8.0 is only as trustworthy as the SF1 sweep that produced it. Hardcoding a per-row constant is correct in kind: in the canonical cost decomposition Cost = n^T·c, the per-unit constants c describe the SYSTEM/HARDWARE and are scale-invariant, while the cardinality vector n (rows, RPCs, bytes) carries the scale-factor dependence. PostgreSQL states this verbatim: cost variables are "measured on an arbitrary scale. Only their relative values matter ... scaling them all up or down by the same factor will result in no change in the planner's choices." Helios's code is exactly this shape — VERIFIED in proxy/ha_lineairdb.hh:336-341 (kC_rpc()=50.0, kC_byte()=0.0008, kC_row()=0.10, kC_probe()=0.05, kC_remote()=0.05, all env-overridable via helios_cost_param), with helios_ref_cost() (lines 364-372) charging add_io(rpc + bytes·kC_byte) and add_cpu(rows·(kC_probe+kC_row)), and kC_materialise()=8.0 (line 356, env HELIOS_C_MATERIALISE) applied per-row ONLY in the non-covering read_cost() branch — VERIFIED line 397: `c.add_cpu(rows * kC_materialise());` inside read_cost() (lines 385-399), which the code comment (lines 388-394) documents as the HA_MRR_INDEX_ONLY non-covering fork while index_scan_cost() (lines 401-406, covering) routes to helios_ref_cost untouched. So tuning C_materialise at SF1 is legitimate PROVIDED it is a true per-row cost: the same per-row value should hold at SF10/SF100 because larger row counts flow through n, not through c. The repo's own M0 data confirms this empirically — the regression does NOT reproduce at SF0.1 and only appears at SF1 (VERIFIED phase22_m0_findings.md:13-22, "the regression does NOT reproduce at SF0.1 — it is SF1-specific"; line 22 "the per-row NLJ penalty scales with N ... a scale-dependent crossover that manifests at SF1"), because the per-row charge stays fixed while cardinality R moves the range-vs-fullscan crossover. The repo's OWN scale-invariance note states it (VERIFIED phase22_m1_findings.md:62-69): "kC_materialise is a per-ROW ratio: the range-vs-fullscan crossover is rows × kC_mat > table_scan ≈ N × per_row_scan, i.e. a fixed FRACTION of the table, independent of N (scale). So it is a SYSTEM/hardware constant (like PostgreSQL random_page_cost), not an SF constant." The TWO caveats that downgrade "not wrong" to "not yet rigorously derived": (1) M1 fit 8.0 against SF1 cardinalities the repo KNOWS are 3-10x biased (q3 est 1500 vs actual 15224 = 10x, VERIFIED phase22_m0_findings.md:44; q10 3x, line 45), so the constant may be silently absorbing cardinality error rather than measuring hardware — that contaminated value is NOT scale-invariant; the repo itself flags this caveat at phase22_m1_findings.md:67-68 ("it was fit against SF1's (3–10× underestimated) cardinality — the wide-ish band gives margin"). (2) The code comment itself (VERIFIED ha_lineairdb.hh:352-355) admits 8.0 is partly a STRUCTURAL flag, not a pure hardware cost: "one row-scaled constant cannot tell a join (materializes rows -> charge right) from an agg-pushdown/GS scan (server aggregates -> charge wrong)," which is why q15 breaks at >=11 (VERIFIED ha_lineairdb.hh:350-352 and the m1 sweep table phase22_m1_findings.md:41-43 showing q15 1.47s at 8 vs 9.96s regressed at 11) and the safe band [8,10] is narrow. A genuine hardware constant has a wide safe band; a narrow band is the symptom of one number doing a discrete job. VERDICT: ship 8.0 as a provisional, env-tunable, calibrated DEFAULT (correctly motivated, the disaggregated analog of Leis multiplying CPU cost by 50x for main-memory), but in M2 re-derive it from isolated micro-benchmarks against TRUE cardinalities and split the structural flag out per access-class so the residual constant is genuinely scale-invariant.

## Why the per-row constant is scale-invariant

The per-row constant is scale-invariant BY CONSTRUCTION, and the rigorous reason is a ratio-of-constants crossover. The optimizer's choice is "materialize a non-covering ref/range (cost ≈ C_materialise·rows_matched + per-row RPC) vs full-scan+prefetch (cost ≈ C_row·N_table + 1-2 bulk RPCs + bytes·C_byte)." Helios's code makes both alternatives LINEAR in row count — VERIFIED table_scan_cost() (ha_lineairdb.hh:374-383) is add_io(kC_rpc + bytes·kC_byte) + add_cpu(rows·(kC_row+kC_remote)), while read_cost() (lines 395-398) is helios_ref_cost + add_io(ceil(rows/kEffBatch)·kC_rpc) + add_cpu(rows·kC_materialise) — so the decision reduces to comparing a per-row materialize charge against a per-row scan charge weighted by selectivity. The breakeven selectivity s* where the plan flips is a RATIO OF CONSTANTS (s* ≈ C_row/C_materialise, modulo the RPC/byte terms) — a DIMENSIONLESS number, a fixed FRACTION of the table, independent of |table| and therefore of SF. Double the SF: both costs double, the crossover fraction is unchanged; the SAME fixed constant correctly yields "fullscan wins" at SF1 (large R) and "range scan fine" at SF0.1 (small R) because cardinality R — not the constant — moved the decision. This is exactly what Helios observed and wrote down: VERIFIED phase22_m0_findings.md:22 ("the per-row NLJ penalty scales with N ... a scale-dependent crossover that manifests at SF1") and phase22_m1_findings.md:64-67 ("the range-vs-fullscan crossover is rows × kC_mat > table_scan ≈ N × per_row_scan, i.e. a fixed FRACTION of the table, independent of N (scale). So it is a SYSTEM/hardware constant ... not an SF constant"). Wu et al. (ICDE 2013) formalize the division of labor: errors in c "reflect an inaccurate view of the underlying hardware" while errors in n "reflect errors in cardinality estimation ... NOT a matter of calibration." Leis et al. (VLDB 2015) close it: with TRUE cardinalities even a trivial tuple-count cost model predicts runtime well, proving the constant is a fixed hardware ratio and scale lives entirely in cardinality. CAVEAT (the honest qualification): scale-invariance holds cleanly ONLY while (i) linearity holds and (ii) the constant was calibrated against UNBIASED cardinality. Two leaks: (a) PostgreSQL's own admission that a hardcoded I/O constant smuggles in a cache/cardinality regime — random_page_cost defaults to 4.0 (not the ~50x raw HDD ratio) because it "assumes mostly cached"; by analogy if C_materialise ever absorbs server-side cache residency it ceases to be SF-invariant. (b) Non-linearity from RPC batching/MRR (per-row round-trip cost falls with batch size — Helios already amortizes via kEffBatch=1024, VERIFIED ha_lineairdb.hh:341,368,396) and cache spill (a remote table cached at SF1 but spilling at SF10). Where these bite, the constant is a local linearization whose valid neighborhood may exclude the deployment SF. THE decisive guard against the cardinality-bias leak: calibrate c with KNOWN n (probe tables of exact row count), never with the optimizer's guessed n — otherwise C_materialise becomes a fudge factor compensating a 3-10x undercount that happens to be ~3x at SF1 (the very risk the repo flags at phase22_m0_findings.md:44-48 and phase22_m1_findings.md:67-68) and will drift as estimates improve or SF changes.

## Methodology classification

INDUSTRY-STANDARD calibration FRAMEWORK applied to Helios-specific cost SIGNALS — neither groping in the dark nor purely novel, and NOT (for M2) something that should be learned/dynamic.

### Industry-standard basis (precedents)

- PostgreSQL planner cost constants — seq_page_cost=1.0 pinned as the unit; random_page_cost=4.0, cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025 set as RATIOS to it. Docs: costs are 'measured on an arbitrary scale. Only their relative values matter ... scaling them all up or down by the same factor will result in no change in the planner's choices.' random_page_cost is recalibrated by STORAGE MEDIUM (SSD -> ~1.1, Momjian PG-docs commit 2020), not by data size — canonical proof the constant is a hardware property. Also the cache caveat: 4.0 (not raw HDD ~50x) 'assumes mostly cached.' (postgresql.org/docs/current/runtime-config-query.html)
- MySQL optimizer cost model — server_cost/engine_cost tables (row_evaluate_cost=0.1, io_block_read_cost, memory_block_read_cost), editable + FLUSH OPTIMIZER_COSTS; manual advises 'try doubling or halving the value and measuring the effect'; disk vs memory params 'reflect the greater cost of processing disk-based tables.' WL#8737 ('IO aware defaults') pins the unit to 'the cost of doing one random io' and DERIVES memory_block_read_cost=0.5 / io_block_read_cost 1.0->2.0 by a regression-gated empirical sweep on DBT3 (TPC-H SF10), rejecting 0.2 (+105% Q20) and 4.0 (Q12 never finished). (dev.mysql.com/doc/refman/8.0/en/cost-model.html; dev.mysql.com/worklog/task/?id=8737)
- TiDB Cost Model — cost = sum of (estimated rows/bytes) x (unit factor); 'scanFactor ... the cost of scanning 1 byte of data on TiKV/TiFlash'; factors 'can be customized by setting system variables like tidb_opt_xxx_factor to fit clusters of different hardware configurations.' v1 round defaults (cpu=3, network=1 per-row transfer, scan=1.5, seek=20 per-request) replaced in Cost Model v2 (default since v6.2.0) by REGRESSION-FITTED non-round constants in plan_cost_ver2.go (TiKVScan=40.70, TiDBCPU=49.90, net=3.96, TiDBRequest=6e6) — non-round values are direct evidence of offline regression calibration. Helios's design doc cites this precedent directly ('TiDB v2 requestFactor 6e6'). (docs.pingcap.com/tidb/stable/cost-model/; pkg/planner/core/plan_cost_ver2.go)
- CockroachDB CBO coster.go — cpuCostFactor=0.01, seqIOCostFactor=1, randIOCostFactor=4 'copied from the Postgres optimizer' with a TODO citing Leis 2015 that the CPU:IO ratio is a hardware property gone stale; plus DIRECT analogs of Helios's remote-access penalties: latencyCostFactor (per-row 'throughput impact of scans on a remotely-located index in a different locality') and DistributeCost=Cost{C:200} (flat 'per-operation cost overhead for ... scans which access remote regions') — per-remote-access additive constants set once as system properties with cardinality supplying the multiplier. (github.com/cockroachdb/cockroach pkg/sql/opt/xform/coster.go)
- Wu, Chi, Zhu, Tatemura, Hacigumus, Naughton — 'Predicting Query Execution Time: Are Optimizer Cost Models Really Unusable?', ICDE 2013 — the canonical calibration-query method: design micro-queries each isolating one cost unit, measure t, solve N c = t; calibration is once-per-system, workload-independent; a calibrated white-box model beat ML predictors 2-4x with no training data. Helios's design doc descends directly from this (NNLS, det(N)!=0 identifiability, VIF — VERIFIED design doc lines 216, 332-333, 343). (pages.cs.wisc.edu/~wentaowu/papers/icde13-prediction.pdf)
- Leis et al., 'How Good Are Query Optimizers, Really?' VLDB 2015 + VLDBJ 2018 — tuned cost model ~41% faster, simple ~34%, both 'dwarfed by' cardinality error; the main-memory retune 'multiply the CPU cost parameters by a factor of 50' is structurally identical to Helios's regime constant; the VLDBJ-2018 disk section REVERSES the headline for I/O-bound systems ('for disk-based systems a good cost model is more important'), which is Helios's RPC-to-remote-storage regime — the random/sequential penalty (= C_materialise) is then the load-bearing constant. Helios's design doc cites this as 'Leis VLDBJ-18: ~41% cost-tuning win when cardinality is right' (VERIFIED line 20). (vldb.org/pvldb/vol9/p204-leis.pdf)

### Novel (Helios-specific) elements

- The disaggregation per-row remote-PK-MATERIALIZATION signal (C_materialise). Classic optimizers have a two-class cost (CPU/IO) and a random-vs-sequential page ratio; Helios adds a THIRD cost class native to disaggregation: the marginal cost of materializing one base row from the remote in-memory server BY PK after a non-covering secondary index narrows the key set. VERIFIED ha_lineairdb.hh:385-398 (read_cost non-covering branch: helios_ref_cost + add_io(ceil(rows/kEffBatch)*kC_rpc) + add_cpu(rows*kC_materialise)) charged ONLY on the non-covering branch, leaving covering index_scan_cost (lines 401-406) untouched. This is the network analog of PostgreSQL's random_page_cost — a non-covering range does R per-row PK fetches where a full-scan+prefetch does 1-2 bulk RPCs — but charged per-MATERIALIZED-ROW. The closest external precedents are CockroachDB's latencyCostFactor and flat DistributeCost=200 (per-remote-access penalties), but Helios's is a per-ROW materialization slope tied to MySQL's covering/non-covering fork (HA_MRR_INDEX_ONLY, documented in the code comment ha_lineairdb.hh:388-394), a more precise signal than a flat per-operation overhead.
- Pinning the REFERENCE UNIT to the RPC round-trip rather than a page fetch. In a disaggregated in-memory system there is no page I/O; the dominant, most-stable hardware primitive is the network round-trip, so C_rpc is the natural unit (the disaggregation analog of MySQL's 'one random io' or PG's seq_page_cost). VERIFIED ha_lineairdb.hh:336 (kC_rpc default 50.0, by far the largest constant, so it dominates per the design doc's 'After calibration C_rpc dominates (TiDB v2 requestFactor 6e6)', design doc line 24). This re-bases the entire ratio system onto the network fabric.
- The access-class-aware MATERIALIZE GATE (planned M2). Recognizing that a single per-row constant conflates a genuine per-row hardware cost with a discrete plan-shape flag (rows materialized to proxy vs server-aggregated/bulk-prefetched), and resolving it by charging C_materialise only when remote PK materialization actually occurs (!remote_grouped_summary AND !prefetch_stageable), with a SINGLE shared predicate called by both the cost path and override_executor_func. VERIFIED as the documented M2 plan: ha_lineairdb.hh:355 'M2 widens it with a prefetch/agg-aware gate' and phase22_m1_findings.md:45-52 'M2 widens it with a prefetch/agg-aware gate (skip or reduce the materialisation charge when the scan feeds a pushed-down aggregate)'. This couples the cost model to Helios's own pushdown/GroupedSummary execution capabilities — a cost SIGNAL that does not exist in any classic optimizer because no classic engine has an agg-pushdown/GroupedSummary alternative to per-row materialization.
- The pairing of records*10-style scan-steering with a per-row materialization penalty as a CALIBRATED PAIR. Helios's table_scan_cost is hooked to ~50 RPC units making scans look expensive (VERIFIED design doc line 16 'table_scan_cost is hooked to ~50 RPC units, so scan is honest-expensive vs probe artificially-cheap'); the prior helios_ref_cost omitted the per-row materialization fanout (CAUSE 2 fixed-batch bug, charging ranges*(kC_rpc/kEffBatch) regardless of real batching), so scans looked expensive while per-row ref looked free (amortized /1024). C_materialise restores the missing half of the pair (VERIFIED phase22_m1_findings.md:23-29 'the cost omitted the materialisation. The added per-row term makes full-scan+prefetch win once R is large'), a disaggregation-specific recalibration of the scan-vs-probe balance analogous to NDB's read_time fanout.

## Static vs dynamic/learned

STATIC, scale-invariant, micro-benchmark-CALIBRATED constants suffice for M2; do NOT build a learned/per-query dynamic cost model. The legitimate "dynamic" elements are narrow and two-fold: (1) per-DEPLOYMENT RECALIBRATION on configuration change (re-run the calibration once when the network, server build, RPC codec, batching policy, or LineairDB record layout changes — Wu's "run once per config"; the design doc already mandates re-deriving the whole protocol after any LineairDB record-layout change, VERIFIED docs/phase22_cost_model_design.md:102 "Commit the whole protocol as a re-runnable script; re-derive after any LineairDB record-layout change"), and (2) runtime CARDINALITY FEEDBACK (adapt the n term, where the real error lives — the repo found 3-10x underestimates, VERIFIED phase22_m0_findings.md:41-48 — via LEO-style execution feedback or post-plan sampling on the CHOSEN plan only). Adapting n is warranted; learning the per-row cost CONSTANT c per query is over-engineering. Three lines of evidence: (a) the split is principled — Vasilenko et al. (arXiv:2409.17136) show CPU-side per-tuple params "do not depend on the current state of the database" (stable, hardcode them) while only the I/O/transfer params drift with buffer-cache state; C_row and C_materialise are CPU/server-side per-row work, so static is correct, and the term most deserving of future adaptivity is C_byte/C_rpc under varying server residency/network load. (b) the upside ceiling is low — Leis et al. (VLDB 2015): a tuned cost model is ~41% faster than stock, a trivial one 34%, and both are "dwarfed by" cardinality error; the marginal return of a learned cost model over a well-calibrated one is small for Helios's handful of fixed access classes. (c) the cost/risk of learned approaches is disproportionate — Neo needs ~thousands of queries / ~24h to match PostgreSQL and can regress ~100x in the tail; even Bao (a practical STEERER, not a from-scratch cost model) needs sliding-window retraining and dedicated robustness engineering (RELOAD 2026, LOAM 2026 catalog why learned optimizers fail in production), all against Helios's hard invariants (1SR, Silo OCC, no cross-tx caching, fail-closed prefetch, MySQL core untouched). RECOMMENDATION: M2 = principled static calibration + regression-banded acceptance; reserve adaptivity for (1) automated per-deployment recalibration and (2) cardinality feedback; defer any learned cost model to a later stage only if static constants prove unstable across deployments.

## M2 calibration methodology (concrete)

1. PIN ONE UNIT, express the rest as RATIOS. Follow MySQL WL#8737 (unit = 'one random io') and PostgreSQL (seq_page_cost=1.0). In a disaggregated system the dominant, most-stable primitive is the RPC round-trip, so set C_rpc as the reference unit and express C_byte, C_row, C_materialise as dimensionless ratios to it. Plan choice depends only on these ratios (PG: 'only their relative values matter'), so the model becomes auto-invariant to absolute-latency scaling and portable across hardware. The decision-relevant quantity is the breakeven selectivity s* ~ C_row/C_materialise — pin and document THAT as the primary tunable ('we full-scan whenever a ref would touch more than s* of the table' is a physically meaningful, SF-independent statement, which the repo already articulates at phase22_m1_findings.md:64-66; '8.0' is not). The constants are already env-tunable via helios_cost_param (VERIFIED ha_lineairdb.hh:329-356).
1. DERIVE each constant from an ISOLATING micro-benchmark, not a whole-query SF1 sweep (Wu ICDE-13; VERIFIED design doc section 7 line 96, 'ACCESS-CLASS-SPLIT ORTHOGONAL MICRO-QUERIES'). Access-class-split orthogonal probes, one dominant unknown per query: (a) C_rpc — vary RPC count at fixed bytes/rows (single point-read intercept); (b) C_byte — fixed rows, vary projected column width; (c) C_rowremote (C_row+C_remote as ONE coefficient, trace cannot split them) — vary range length at fixed projection/n_rpc; (d) C_probe — ref-row residual slope minus C_rowremote; (e) kRefSecondary — the KEY pair: a covering scan (secondary_flag=0) vs a NON-covering scan (flag=1) over the SAME key and SAME row count so the flag is identifiable; (f) B_eff (effective batch) grid-searched OUTSIDE the linear fit (it sits inside a ceil()). Anchor every slope to a MySQL cost unit via local ROW_EVALUATE_COST=0.1 (VERIFIED design doc line 98 'Anchor units at ROW_EVALUATE_COST=0.1') so constants stay data-size independent.
1. CALIBRATE AGAINST TRUE CARDINALITIES ONLY — the single most important guardrail. Use COUNT(*)-known probe tables so n is exact (Wu's Completeness/Simplicity). The repo records 3-10x cardinality underestimates at SF1 (VERIFIED phase22_m0_findings.md:44-48: q3 est 1500 vs actual 15224 = 10x, q10 3x); if C_materialise is tuned so plans 'look right' under biased estimates it absorbs the bias and is no longer scale-invariant. If the from-physics C_materialise lands near 8, the M1 value was 'right for the right reason'; if it lands far from 8, the current value was compensating cardinality error and WILL drift with SF. Add a STATS-HEALTH precondition (VERIFIED design doc line 16 'M0/M2 add EXPLAIN ANALYZE actual-vs-estimated outer-row checks' and line 63 'Cardinality-health precondition into M2'): at M0/M2 capture EXPLAIN ANALYZE actual-vs-estimated outer rows for q3/q5/q7/q8/q18; if error > ~2x, fix cardinality before trusting cost.
1. FIT BY NON-NEGATIVE LEAST SQUARES WITH IDENTIFIABILITY GATES. Stack rows of (n_rpc, bytes, n_rows, secondary_flag) with median+p95 us as y (>=5 warm-then-measure reps), solve NNLS (VERIFIED design doc line 98). ADDRESS COLLINEARITY (VERIFIED line 98): C_rpc/C_probe/kRefSecondary/B_eff are collinear on per-row secondary-ref plans and C_byte/C_rowremote on fixed-width scans, so each micro-query must vary one factor independently (Wu det(N)!=0). REPORT design-matrix condition number, per-constant 95% CIs, and per-column VIF (VERIFIED lines 98, 115, 136); REJECT and redesign any micro-query whose constant has a CI spanning an order of magnitude or VIF above threshold. Fit engine_cost SEPARATELY from an eq_ref-only micro-bench, NOT the byte-scan NNLS (VERIFIED design doc lines 97, 134, 181, 207: opt_costmodel mixes table_in_memory_estimate with buffer/io_block, so it is not linear in the same coefficients — Reviewer-2 BI-7).
1. WIDEN THE q15 WINDOW BY GATING THE MATERIALIZE CHARGE PER ACCESS-CLASS, not by finding a better number. The narrow [8,10] band exists because one row-scaled constant cannot distinguish a join that materializes base rows to the proxy from an agg-pushdown/GroupedSummary scan that the server aggregates in bulk (VERIFIED ha_lineairdb.hh:352-355 and phase22_m1_findings.md:45-52 'M2 widens it with a prefetch/agg-aware gate'). Charge C_materialise ONLY when access_is_range_or_ref AND requires_base_row_by_pk AND !covering AND !remote_grouped_summary AND !prefetch_stageable; else set materialise_rows=0 and cost with C_rpc/C_byte/C_row only. Model prefetch as batch RPCs + bytes + residual row CPU (ceil(rows/B_eff)·C_rpc), NOT rows·C_materialise, when Helios can stage PKs and bulk-fetch. Factor a SINGLE shared predicate (helios_can_grouped_summary / prefetch-stageable detector) called by BOTH the cost path and override_executor_func so cost and execution never disagree; if context is missing at cost time, stash a per-THD/per-table capability bit beforehand or fail conservatively (no charge). Once the constant no longer encodes a discrete plan-shape flag its safe band widens and it becomes genuinely scale-invariant.
1. VERIFY SCALE-INVARIANCE EMPIRICALLY by re-running the SAME calibration probes at >=2 scale factors (SF0.1, SF1, SF3/SF4) and requiring the FITTED constants (not the plans) to be stable to within measurement noise. If C_materialise drifts with SF, that is the signal it absorbed a fixed/amortization or cache-spill effect — refactor that effect into C_rpc/a batch-amortization term or a piecewise residency-dependent component (the PostgreSQL random_page_cost=4.0 trap). This single experiment directly answers the user's worry: scale-invariance is a testable hypothesis, not an assumption; the repo's own M0 already provides the SF0.1-vs-SF1 contrast establishing the crossover is cardinality-driven (phase22_m0_findings.md:13-22).
1. KEEP THE REGRESSION-GATED SAFE-BAND ACCEPTANCE TEST and harden it (it IS the WL#8737 industry method, and matches the M1 sweep already run at phase22_m1_findings.md:36-43). An accepted constant must (i) be regression-free across the full 22-query suite, (ii) sit in the INTERIOR of a band (not on a cliff edge — q15's cliff at >=11 is the cautionary case), at >=2 SFs, and (iii) survive leave-one-query-out CV plus a 2-10x prefix_rowcount/rec_per_key perturbation that does not flip the scan-vs-NLJ choice (VERIFIED design doc line 102 'fit to PLAN-CHOICE with a margin SIZED by perturbation, not a fixed 0.5x ratio -- perturb prefix_rowcount/rec_per_key by 2-10x ... leave-one-query-out CV across the 22-suite', Flow-Loss). Size the scan-vs-NLJ margin so the choice is robust to the very cardinality errors a learned model would otherwise be invoked to paper over.
1. DOCUMENT EVERY CONSTANT AS A CALIBRATED DEFAULT WITH PROVENANCE, NOT A CONSTANT OF NATURE. Each is already env-tunable (VERIFIED ha_lineairdb.hh:329-356: HELIOS_C_RPC, HELIOS_C_BYTE, HELIOS_C_ROW, HELIOS_C_MATERIALISE, HELIOS_BATCH); add a FLUSH-equivalent reload (mirroring mysql.engine_cost + FLUSH OPTIMIZER_COSTS). MySQL's own defaults drifted across versions (io_block_read_cost 1.0<->2.0) as hardware assumptions changed, so annotate 8.0 with the calibration date, hardware, network, server build, SF, and band. Commit the WHOLE protocol as a re-runnable script keyed on a hardware+record-layout fingerprint; re-derive on config change (VERIFIED design doc line 102), NEVER per-workload or per-SF (re-deriving per-SF would be a category error — SF changes n, not c).
1. SPEND THE NEXT INCREMENT ON CARDINALITY, NOT MORE COST TUNING. Leis 2015/2018/2024 is unambiguous: once cardinalities are good, even a trivial static cost model suffices, and the cost-model upside (~41%) is dwarfed by cardinality error. The repo's 3-10x underestimates (q3/q10, VERIFIED phase22_m0_findings.md:44-48) are the higher-leverage defect, and the repo's own diagnosis flags this as an 'Open risk per Leis (cost=guardrail, cardinality=steering)' (line 48). A correctly-calibrated C_materialise plus better records/rec_per_key estimates beats any amount of further fiddling with the constant. The warranted adaptive investment is runtime cardinality feedback (LEO-style or post-plan sampling on the chosen plan), NOT a learned per-query cost model.

## Pitfalls to avoid

- CARDINALITY CONTAMINATION (the primary trap). M1 fit 8.0 against SF1 cardinalities the repo KNOWS are 3-10x biased (VERIFIED phase22_m0_findings.md:44-48: q3 est 1500 vs actual 15224 = 10x; q10 3x; and the repo's own caveat at phase22_m1_findings.md:67-68 'it was fit against SF1's (3–10× underestimated) cardinality'). If C_materialise is tuned so plans 'look right' under biased estimates, it silently absorbs the bias and is NO LONGER scale-invariant — a fudge factor compensating an undercount that happens to be ~3x at SF1 and will drift as estimates improve or SF changes. Mitigation: calibrate c with KNOWN n (COUNT(*)-exact probe tables) and add an EXPLAIN-ANALYZE stats-health precondition (actual-vs-estimated within ~2x, VERIFIED design doc line 63) before trusting cost.
- STRUCTURAL OVERLOAD / narrow band. 8.0 is partly a discrete plan-shape flag (materialize-to-proxy vs server-aggregate), not a pure hardware cost — q15 breaks at >=11 because its non-covering l_shipdate range is bulk-prefetched/server-aggregated, not per-row materialized (VERIFIED ha_lineairdb.hh:350-355 and phase22_m1_findings.md:41-52, sweep table showing q15 1.47s at 8 vs 9.96s at 11). A narrow safe band [8,10] is the symptom (VERIFIED phase22_m1_findings.md:43 'Safe band ≈ [8, 10]'). Do NOT chase a better single number; split the charge per access-class (the M2 gate). Get the gate's predicate IDENTICAL between cost path and executor (override_executor_func) or cost and execution disagree.
- NON-LINEARITY breaking scale-invariance: (a) RPC batching/MRR — a flat per-row C_rpc over-penalizes large batches and shifts the very crossover C_materialise governs; model per-row RPC as round_trip/B_eff + C_byte*bytes (Helios amortizes via kEffBatch=1024, VERIFIED ha_lineairdb.hh:341,396, but B_eff must be measured, not assumed). (b) Cache/working-set — a remote table cached at SF1 but spilling at SF10 changes effective random-access cost, so C_materialise becomes residency-dependent (the PostgreSQL random_page_cost=4.0 'mostly cached' trap). Test by re-fitting at >=2 SFs; if it drifts, split into a piecewise residency-dependent term.
- CALIBRATION IDENTIFIABILITY / collinearity. C_rpc/C_probe/kRefSecondary/B_eff are collinear on per-row secondary-ref plans; C_byte/C_rowremote on fixed-width scans (VERIFIED design doc line 98). A naive joint regression yields an ill-conditioned, non-identifiable fit. Each micro-query must vary one factor independently (Wu det(N)!=0); report condition number, per-constant 95% CIs, per-column VIF (VERIFIED lines 98, 115, 136); reject and redesign any constant with a CI spanning an order of magnitude. Fit engine_cost SEPARATELY (eq_ref micro-bench), NOT from the byte-scan NNLS — opt_costmodel mixes table_in_memory_estimate with buffer/io_block and is not linear in the same coefficients (VERIFIED lines 97, 207, Reviewer-2 BI-7).
- OVER-FITTING to the regressors. If you fit on q3/q5/q7/q8 themselves you tune to those plans, not to the hardware. Use leave-one-query-out CV (VERIFIED design doc line 102), plus a 2-10x prefix_rowcount/rec_per_key perturbation that must not flip scan-vs-NLJ (Flow-Loss: fit to plan-CHOICE with a perturbation-sized margin, not Q-error, VERIFIED line 102). A fixed 0.5x safety margin is insufficient — a 2-10x cardinality miss can swamp it (Reviewer-2 BI-8, VERIFIED design doc line 20).
- WHOLE-QUERY SWEEP MASQUERADING AS DERIVATION. The M1 single-SF plan-flip sweep is VALIDATION, not derivation — the repo itself labels it 'M1 quick sweep; M2 does it rigorously' (VERIFIED phase22_m1_findings.md:31) and PostgreSQL's docs explicitly warn 'changing them on the basis of just a few experiments is very risky.' Treating 8.0 as derived-from-first-principles when it is reverse-engineered from observed plan outcomes is the methodological error M2 must correct.
- PREMATURE LEARNED/DYNAMIC COST MODEL. Jumping to Bao/Neo-class learning for the per-row constant is over-engineering: hours of training, sliding-window retrain infra, tail-regression risk (RELOAD/LOAM 2026 document why learned optimizers fail in production), against Helios's 1SR/no-cross-tx-cache invariants — for an upside Leis bounds at ~41% and 'dwarfed by cardinality.' Adapt n (cardinality feedback), not c (per-row cost), and only after static calibration is exhausted.
- TREATING 8.0 AS ETERNAL. MySQL's own defaults drifted (io_block_read_cost 1.0<->2.0) as hardware assumptions changed. Document 8.0 with calibration provenance (date, hardware, network, server build, SF, band) and re-derive on config/record-layout change (VERIFIED design doc line 102 're-derive after any LineairDB record-layout change') — NEVER per-workload or per-SF (re-deriving per-SF is a category error: SF changes n, not c).
