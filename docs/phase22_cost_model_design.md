## 2. Target model — guiding principle

Cost is the guardrail, cardinality is steering (Leis VLDBJ-18: ~41% cost-tuning win when cardinality is right). But best_access_path can PRUNE the scan/range alternative before a corrected cost is compared (Reviewer-2 BI-2, VERIFIED: find_best_ref breaks early on a UNIQUE/CLUSTERED_PK eq_ref via heuristic_eqref_already_found sql_planner.cc:412-415 and :728-730; scan pruned via heuristic_index_cheaper :1114), so pricing alone is necessary but not sufficient. THREE-LAYER principle: (i) make RPC-minimizing plans cheap and bare per-row NLJ expensive via PER-SITE authoritative levers; (ii) PROVE via optimizer trace the scan/hash/MRR candidate was enumerated and compared, not pruned; (iii) where pruning still defeats out-costing under outer-cardinality underestimate, ESCALATE to optimizer_switch BKA conversion that turns the surviving per-row ref into batched access. Cost basis is C_rpc*real-round-trips + C_byte*bytes, round-trips PER ACCESS PATH (1 scan/prefetch; ceil(keys/B_eff) for genuine PK-MRR or BKA; outer-rows for bare per-row ref), never a fixed divide-by-1024. CONFLICT RESOLUTION, PER-SITE LEVERS WITH CORRECTED ORTHOGONALITY (resolves Reviewer-1 BI-1/BI-2/BI-3 and reopens open_question 4): eq_ref (sql_planner.cc:433, the SINGLE relevant site; fulltext :682-684 dropped) is reachable ONLY via Cost_model_table page_read_cost, so mysql.engine_cost is the SOLE MANDATORY lever there. Non-covering secondary ref (sql_planner.cc:163) calls handler page_read_cost, so the OVERRIDE is authoritative there. CRITICAL CORRECTION: orthogonality is NOT guaranteed by construction. Because default handler::page_read_cost delegates to the same engine_cost constants (handler.cc:6083-6084), engine_cost reaches :163 too UNTIL the override is installed. Therefore the override ESTABLISHES orthogonality: once page_read_cost is overridden, :163 is governed by the override (engine_cost-independent) while :433 stays engine_cost-bound. The proof order is reversed from before: M4b installs the override FIRST (intercepts :163), then M4a varies engine_cost with the override PRESENT and shows only q7 moves. ACCESS-CLASS SPLIT (Reviewer-2 suggestion + BI-3): the model is split by access class -- eq_ref, non-covering-secondary ref, covering ref, range scan, table scan, PK-MRR/BKA batch, pushdown/hash -- not a single blanket secondary penalty. Covering refs route to index_scan_cost (:151-155) and are NOT touched by the page_read_cost override, so index-only access is preserved (Reviewer-2 BI-3 over-correction risk eliminated by construction). PRESERVE BENEFICIAL INDEXES: divide-by-B_eff stays ONLY at the PK-MRR site (engine-native batching guarantees coalescing, q21 SIP/IN-lists not over-charged); records_in_range floors a NON-UNIQUE single-row estimate to 2 but returns 1 for proven-unique full-key and never clamps selective/multi-row/batchable ranges (Reviewer-2 BI-4 truly-selective safety); q21 SIP/covering preserved by a PLAN-CHOICE GATE (trace enumerated-and-chosen + rpc-trace few-RPC), not a whitelist (Reviewer-2 BI-6). Every regressing plan loses by a SAFETY MARGIN against cardinality error: rather than a fixed 0.5x ratio (which Reviewer-2 BI-8 notes a 2-10x prefix_rowcount miss can swamp), the margin is sized so the scan/hash plan stays cheaper across a 10x perturbation of prefix_rowcount/rec_per_key (Flow-Loss; validated by perturbation CV, not asserted).

## 3. Cost formula (per access class)

PER-ACCESS-CLASS cost in MySQL Cost_estimate dimensions (io carries RPC+transfer and dominates; cpu carries materialize+probe). row_bytes = helios_row_bytes (mean_rec_length, floor 64); n_rpc = real round-trip count. (1) TABLE SCAN / PREFETCH (table_scan_cost): io = C_rpc + rows*row_bytes*C_byte; cpu = rows*C_rowremote; n_rpc=1. (2) BATCHED PK KEY ACCESS (multi_range_read_info_const/info, proxy engine-native, gated keyno==primary_key && !prefetch, ha_lineairdb.cc:4099-4137): n_rpc = ceil(n_keys/B_eff), B_eff = HELIOS_BATCH_BYTES/row_bytes (NDB byte-budget ~32768); io = n_rpc*C_rpc + rows*row_bytes*C_byte; cpu = rows*(C_probe+C_rowremote). Secondary refs never reach here (custom path gates on PK full-key; else DS-MRR). (3) BARE PER-ROW eq_ref INNER (sql_planner.cc:433, engine_cost-bound, NOT handler-overridable): cur_fanout=1.0, charge = prev_record_reads * page_read_cost(1.0); the lever is engine_cost set so page_read_cost(1.0) after in_mem weighting ~= C_rpc, making outer_rows eq_ref lookups cost ~outer_rows*C_rpc. (4) NON-COVERING SECONDARY REF (sql_planner.cc:163, handler page_read_cost): the index-to-PK double-read. Priced ENTIRELY in the page_read_cost(uint index, double reads) OVERRIDE (the find_cost_for_ref site), NOT in read_cost/index_scan_cost (Reviewer-1 BI-3 relocation). Override returns read_cost(index,1,reads).total_cost() (NDB :7293) scaled by reads, with the secondary double-hop as an INTERACTION TERM (Reviewer-2 BI-5): io_secondary = io_base*(1 + kRefSecondary*secondary_flag), secondary_flag in {0,1}, kRefSecondary ~1.0 one fitted coefficient (NOT a free multiplier). secondary_flag = (key != primary_key && !covering_keys.is_set(key)). worst_seek_times(double reads) override (NO index arg, handler.h:5088, Reviewer-2 BI-4) returns page_read_cost(UNDEFINED_INDEX=MAX_KEY+1, max(reads,1)) (NDB :7306) where read_cost internally picks the WORST index, so the worst_seeks cap at :163 cannot under-price the secondary ref; the override resolves the worst index itself. Both classic and hypergraph route here via find_cost_for_ref (cost_model.cc:88), but hypergraph passes worst_seeks=DBL_MAX so the min collapses to page_read_cost alone (worst_seek_times inert in hypergraph; load-bearing only in classic). (5) COVERING REF (sql_planner.cc:154): routes to index_scan_cost, NOT touched by the page_read_cost override; priced as index-only transfer (no PK double-hop, secondary_flag=0), preserving legitimate index-only access (Reviewer-2 BI-3). (6) read_cost/index_scan_cost CORRECTIONS still apply for the paths that DO use them: range_optimizer (range_optimizer.cc:616,871), force-index scan (:843), and the hypergraph EQ_REF/REF AccessPath leaf costing; here helios_ref_cost charges n_rpc = ranges UN-amortized (full C_rpc per range) so a bare per-row range/ref priced through these is honest; amortization lives ONLY in multi_range_read_info (PK). GUARDED CARDINALITY (records_in_range): 1 for proven-unique full-key equality (HA_NOSAME, all parts, no NULL); else for a NON-UNIQUE single-row estimate floor at 2 (NDB clamp :12861-12912); NEVER floor a multi-row or selective or proven-batchable range (Reviewer-2 BI-4: do not clamp truly-selective ranges). SELECTIVITY CROSSOVER: NLJ wins only when outer_rows_after_filter*C_rpc < C_rpc + scanned_bytes*C_byte; optional Spark-style HELIOS_BULK_ROWS_THRESHOLD. IDENTIFIABLE CONSTANTS (Reviewer-2 BI-5/BI-7): fit C_rpc, C_byte, C_rowremote (C_row+C_remote as ONE coefficient; trace cannot split), C_probe (ref-row residual minus C_rowremote), kRefSecondary (interaction coefficient on the 0/1 flag); B_eff measured/grid-searched OUTSIDE the linear fit (inside ceil). engine_cost io/memory are NOT free-fit from the SAME regression as the override (Reviewer-2 BI-7: opt_costmodel mixes table_in_memory_estimate with buffer/io_block, so deriving engine_cost from the byte-scan fit is unsound); instead engine_cost is fit by a SEPARATE eq_ref-only micro-bench (target: page_read_cost(1.0) per-probe charge ~= measured per-eq_ref-lookup RPC us), and the two levers are unit-reconciled by requiring M4a/M4b to land q7 and q3/q5/q8 at the same C_rpc-scale per-probe cost. After calibration C_rpc dominates (TiDB v2 requestFactor 6e6).

## 4. Handler overrides (the methods to change)

### `mysql.engine_cost(io_block_read_cost, memory_block_read_cost) for LINEAIRDB (SQL lever, MANDATORY for eq_ref ONLY)`

- **Purpose:** Close the eq_ref bypass at the SINGLE relevant site sql_planner.cc:432-434 (the fulltext :682-684 site is dropped per Reviewer-1 BI-1). page_read_cost(1.0) there reads ONLY io_block_read_cost/memory_block_read_cost (opt_costmodel.cc:79-93); no handler virtual is consulted, so this is the only lever reaching eq_ref.
- **Proposed behavior:** Raise BOTH io_block_read_cost and memory_block_read_cost to the C_rpc-scale value fit by a SEPARATE eq_ref micro-bench (NOT derived from the same byte-scan NNLS, Reviewer-2 BI-7) so prev_record_reads*page_read_cost(1.0) ~= prev_record_reads*C_rpc; both raised because the in_mem split is table-size-dependent (ha_lineairdb.cc:3226). Column-listed re-runnable upsert applied before the measured session connects, then FLUSH OPTIMIZER_COSTS. WARNING (Reviewer-1 BI-2): with the page_read_cost override ABSENT this ALSO raises the non-covering-secondary site :163 because default handler::page_read_cost delegates to the same constants (handler.cc:6083-6084); orthogonality is only achieved once the override below is installed. WARNING (Reviewer-2 BI-1): engine_cost moves ALL eq_ref lookups together including small-outer NLJ that are good; the records_in_range guard plus the selectivity crossover, not engine_cost alone, must keep genuinely tiny eq_ref lookups cheap.

### `page_read_cost(uint index, double reads) handler virtual -- authoritative for NON-COVERING SECONDARY REF in BOTH optimizers`

- **Purpose:** Close the secondary-ref bypass at sql_planner.cc:163 (min of handler page_read_cost(keyno,num_rows) and worst_seeks), which IS the handler virtual (handler.h:5077). VERIFIED both the classic planner (find_cost_for_ref) and the hypergraph optimizer (EstimateRefAccessCost->find_cost_for_ref, cost_model.cc:88) route here; the override is load-bearing for both. This is the relocation of the kRefSecondary term FROM read_cost/index_scan_cost (Reviewer-1 BI-3, which never reaches the find_cost_for_ref site) TO here.
- **Proposed behavior:** Return read_cost(index,1,reads).total_cost() (NDB :7293) scaled by reads, with the non-covering double-hop as an INTERACTION term io_base*(1 + kRefSecondary*secondary_flag), secondary_flag = (index != primary_key && !covering_keys.is_set(index)) so covering refs (flag 0) are NOT penalized; amortized over B_eff ONLY when the path is genuinely batched, never flat (flat regressed q10/q3 in phase-9). Installing this override is what makes engine_cost stop reaching :163, ESTABLISHING the per-site orthogonality (Reviewer-1 BI-2). Gate behind helios_cost_v2_on.

### `worst_seek_times(double reads) handler virtual, NO index parameter`

- **Purpose:** The worst_seeks ceiling in find_cost_for_ref (sql_planner.cc:163, classic planner only); default caps secondary-ref cost too low. Signature has no index arg (handler.h:5088, Reviewer-2 BI-4). NOTE: in the hypergraph optimizer worst_seeks=DBL_MAX (cost_model.cc:89) so this override is INERT there; it is load-bearing only for the classic planner the SF1 harness uses.
- **Proposed behavior:** Override the NDB way (:7306): return page_read_cost(UNDEFINED_INDEX=MAX_KEY+1, max(reads,1)) where read_cost internally selects the WORST index; the override resolves the worst index itself and takes no index argument -- a conservative same-unit upper bound that cannot under-price a non-covering secondary ref. Gate behind helios_cost_v2_on.

### `helios_ref_cost(double ranges, double rows) private helper feeding read_cost and index_scan_cost`

- **Purpose:** Fix the fixed-1024 amortization (ha_lineairdb.hh:348-356) for the paths that DO use read_cost/index_scan_cost: range_optimizer, force-index scan, and hypergraph REF/EQ_REF leaf costing. NOTE: this is NOT the q3/q5/q8 find_cost_for_ref fix (that is the page_read_cost override above) -- correcting Reviewer-1 BI-3's mis-placement.
- **Proposed behavior:** Charge n_rpc as ranges UN-amortized (full C_rpc per range); io = ranges*C_rpc + rows*row_bytes*C_byte; cpu = rows*(C_probe+C_rowremote). Move divide-by-B_eff amortization EXCLUSIVELY to multi_range_read_info (PK only). M3 gate must diff q10 AND q3 latency vs the noidx baseline (replays the phase-9 flat-per-ref shape in isolation).

### `read_cost(uint index, double ranges, double rows) and index_scan_cost(uint index, double ranges, double rows)`

- **Purpose:** Currently identical (both call helios_ref_cost), missing un-amortized RPC. They govern range_optimizer (range_optimizer.cc:616,871), force-index scan (:843), and the hypergraph join leaf -- NOT the classic find_cost_for_ref secondary-ref site (Reviewer-1 BI-3).
- **Proposed behavior:** Route through corrected helios_ref_cost (un-amortized C_rpc per range). Do NOT place the kRefSecondary interaction term here for the classic-planner q3/q5/q8 fix (it would not reach :163); the secondary penalty lives in the page_read_cost override. If hypergraph_optimizer is ever enabled, ADD the kRefSecondary flag here too because hypergraph EQ_REF/REF leaf costing can consult these directly -- gate that addition on the hypergraph switch.

### `multi_range_read_info_const and multi_range_read_info`

- **Purpose:** PK-only sites where proxy engine-native batching (ha_lineairdb.cc:4150-4239) guarantees coalescing; currently flat add_io(1.0) (ha_lineairdb.cc:4099-4137) gated keyno==primary_key && !prefetch.
- **Proposed behavior:** Replace flat 1.0 with io = ceil(n_keys/B_eff)*C_rpc + rows*row_bytes*C_byte; cpu = rows*(C_probe+C_rowremote); B_eff = HELIOS_BATCH_BYTES/row_bytes. Amortized RPC legitimately lives here (engine-native batch, not stock DS-MRR). Secondary-ref pricing does not flow through here (PK-only gate).

### `records_in_range(uint inx, key_range min, key_range max)`

- **Purpose:** Prevent the rows==1-means-NLJ-free misestimate without over-shrinking batchable OR truly-selective ranges (Reviewer-2 BI-4).
- **Proposed behavior:** Return 1 for proven-unique full-key equality (HA_NOSAME, all parts, no NULL); for a NON-UNIQUE single-row estimate floor at 2 (NDB clamp :12861-12912); NEVER floor a multi-row, selective, or proven-batchable range (q21 l_sk/SIP and selective range predicates must keep their real low estimate). Gate the floor to known zero/one estimates only (Reviewer-2 suggestion).

### `scan_time and read_time deprecated fallback`

- **Purpose:** NDB-ported, never calibrated; active only when COST_V2 OFF.
- **Proposed behavior:** Retire as default by flipping HELIOS_COST_V2 default ON after un-hooked paths are covered and calibration+pruning gates pass; leave intact for rollback.

## 6. What to disfavor (and how the model achieves it)

- Bare per-row eq_ref NLJ inner lookups (1 RPC per outer row): eq_ref (the SINGLE site sql_planner.cc:433, fulltext :682-684 NOT a site) made expensive via the raised mysql.engine_cost (the only lever reaching it); a high-fanout eq_ref NLJ costs ~outer_rows*C_rpc and loses to scan+hash. records_in_range (unique->1, else floor 2) plus the selectivity crossover keep a genuinely tiny eq_ref lookup cheap so engine_cost coarseness (Reviewer-2 BI-1) does not over-penalize good small-outer NLJ.
- Non-covering secondary-index probe + PK materialize charged ~2x via the kRefSecondary INTERACTION term, priced in the page_read_cost OVERRIDE at the find_cost_for_ref site :163 (NOT read_cost/index_scan_cost, which never reach that site -- Reviewer-1 BI-3); covering refs (secondary_flag 0, routed to index_scan_cost :154) are NOT penalized (Reviewer-2 BI-3); TiDB IndexLookUp, NDB UNIQUE fanout.
- Bare per-row ref/range priced through read_cost/index_scan_cost (range_optimizer, force-index scan, hypergraph leaf): charged n_rpc as ranges UN-amortized so it is honest there; amortization is moved exclusively to the PK-MRR site.
- Plans that abandon pushdown or SIP: an index-NLJ that loses GroupedSemijoin (q18) or agg-pushdown (q1/q6) costed at full un-pushed remote transfer, so it never out-prices the pushdown plan.
- rows==1-means-free misestimates for NON-UNIQUE single-row point access: records_in_range floor-at-2 prevents a non-unique FK ref from pricing as unique (q5 NLJ-cascade trigger) WITHOUT clamping selective, multi-row, batchable, or proven-unique full-key access (q21 SIP/IN-lists and truly-selective ranges not over-charged -- Reviewer-2 BI-4).
- RELYING ON OUT-COSTING ALONE when the optimizer prunes the scan/range alternative before costing it (heuristic_eqref_already_found, heuristic_index_cheaper): the BKA escalation (optimizer_switch) is LOAD-BEARING not optional (Reviewer-2 BI-2) -- turn the surviving per-row ref into batched ~1-RPC-per-batch access rather than betting the cost term is even compared.
- Deriving engine_cost from the same NNLS as the byte-scan override (Reviewer-2 BI-7): opt_costmodel mixes table_in_memory_estimate with buffer_block/io_block, so engine_cost must be fit by a separate eq_ref micro-bench, not the byte/row regression.
- A fixed 0.5x safety-margin ratio as the sole cardinality guard (Reviewer-2 BI-8): a 2-10x prefix_rowcount miss can swamp it; the margin is sized by 2-10x perturbation CV and backed by the records_in_range guard and an EXPLAIN-ANALYZE cardinality-health precondition.

### Axis A — MySQL 8.0 optimizer cost model internals & tunable constants (and how Helios can lever them to make scan+hash+batched beat per-row NLJ without patching MySQL core)

- COMPLETE DEFAULT COST CONSTANTS (primary source: third_party/mysql-server/sql/opt_costconstants.cc lines 56-152). server_cost: row_evaluate_cost=0.1, key_compare_cost=0.05, memory_temptable_create_cost=1.0, memory_temptable_row_cost=0.1, disk_temptable_create_cost=20.0, disk_temptable_row_cost=0.5. engine_cost: memory_block_read_cost=0.25, io_block_read_cost=1.0. These are the compiled-in defaults; mysql.server_cost / mysql.engine_cost rows with non-NULL cost_value override them, NULL means use the default (cost-model.html).
- THE SMOKING GUN — Helios's COST_V2 handler hook is STRUCTURALLY BYPASSED for the exact plans that regress. In best_access_path, the eq_ref path (sql_planner.cc:432-433) computes inner-lookup IO as `cur_read_cost = prev_record_reads(join,idx,table_deps) * table->cost_model()->page_read_cost(1.0)`. This calls page_read_cost (→ io_block_read_cost, default 1.0) DIRECTLY, NOT the handler's read_cost()/index_scan_cost() overrides. So q7's '5-stage NLJ + per-row PRIMARY lookup' (all eq_ref) is priced as prefix_rows × 1.0 IO units — completely outside HELIOS_COST_V2. This is the root reason COST_V2 'is insufficient even when ON'.
- SECONDARY-INDEX ref is ALSO mostly bypassed. find_cost_for_ref (sql_planner.cc:143-164) routes cost by case: (a) covering index → index_scan_cost() [HOOKED]; (b) clustered-PK full match → read_cost() [HOOKED]; (c) ELSE (the common non-covering secondary index → PK-lookup case) → `min(table->file->page_read_cost(keyno, num_rows), worst_seeks)` [NOT HOOKED — page_read_cost and worst_seek_times are deliberately NOT overridden per ha_lineairdb.hh:382-386]. So the typical 'secondary index probe + PK lookup' NLJ that regresses q3/q5/q8 is priced through page_read_cost/io_block_read_cost, NOT helios_ref_cost. The COST_V2 trio (table_scan_cost/read_cost/index_scan_cost) cannot reach it.
- THE TABLE-SCAN SIDE IS FULLY HOOKED, so the optimizer compares an honest (high) Helios scan cost against an artificially CHEAP (un-hooked, io_block_read_cost=1.0-priced) ref/eq_ref cost — guaranteeing it flips to NLJ. best_access_path scan branch (sql_planner.cc:838-893): single_scan_read_cost = table_scan_cost() [HOOKED to ~50 RPC units], then scan_and_filter_cost = buffer_count × (single_scan_read_cost + row_evaluate_cost(rows)). Meanwhile ref cost = prefix_rowcount × find_cost_for_ref(...) where the per-lookup term is ~num_rows × io_block_read_cost(1.0) un-hooked. The asymmetry (scan hooked-expensive, ref un-hooked-cheap) is precisely what drives the 39→77s regression.
- ZERO-CODE PER-ENGINE LEVER CONFIRMED VIABLE. opt_costconstants.cc:289-322 (update_engine_cost_constant → find_handler_slot_from_name → ha_resolve_by_name) proves UPDATE/INSERT on mysql.engine_cost with engine_name = the plugin name binds io_block_read_cost / memory_block_read_cost PER-ENGINE without touching MySQL core. Helios's plugin name is 'LINEAIRDB' (proxy/ha_lineairdb.cc:4585). Because the regressing eq_ref/secondary-ref paths price through page_read_cost → io_block_read_cost, RAISING io_block_read_cost for LINEAIRDB is the ONE lever that actually reaches them. Caveat: in-memory estimate. page_read_cost blends io_block_read_cost (on-disk fraction) and memory_block_read_cost (in-mem fraction) by table_in_memory_estimate(); RAISE BOTH constants for LINEAIRDB so the per-row-probe charge rises regardless of the in-memory split.
- BKA/MRR IS THE JOIN-METHOD LEVER THAT MATCHES HELIOS'S BATCHED RPC STRENGTH, AND IT IS OFF BY DEFAULT. Batched Key Access submits a whole join_buffer_size batch of keys to the engine via one MRR call (≈1 RPC per batch) instead of 1 lookup per outer row. Requirements (bnl-bka-optimization.html): batched_key_access=on, mrr=on, mrr_cost_based=off (MRR's built-in cost estimate is 'too pessimistic', so it must be forced off). Default: batched_key_access=off. This is the canonical mechanism to legitimize ref-NLJ in a disaggregated engine — it turns the hostile per-row probe into the batched key access Helios already implements (multi_range_read_init).
- page_read_cost INTERNAL FORMULA (opt_costmodel.cc:79-91): cost = buffer_block_read_cost(pages×in_mem) + io_block_read_cost(pages×(1-in_mem)), where in_mem=table_in_memory_estimate() ∈[0,1] and buffer_block_read_cost = pages×memory_block_read_cost. So for an in-memory table (in_mem→1) the per-page charge collapses to memory_block_read_cost=0.25 — making un-hooked ref lookups even CHEAPER. find_worst_seeks (sql_planner.cc:5882-5892) caps secondary-ref cost at min(worst_seek_times(num_rows/10), table_scan_cost×3) with a floor of worst_seek_times(2.0); worst_seek_times default = page_read_cost(reads), also un-hooked.
- handler DEFAULT cost methods (handler.cc:6030-6099) that Helios overrides: table_scan_cost()=scan_time()×page_read_cost(1.0); index_scan_cost()=index_only_read_time(index,rows)×page_read_cost_index(index,1.0); read_cost()=read_time(...)×page_read_cost(1.0). Note these defaults multiply the deprecated scan_time()/read_time() by page_read_cost — so even the legacy path is io_block_read_cost-scaled. Helios replaces them with RPC+byte cost, but cannot replace page_read_cost itself where the optimizer calls it directly (the eq_ref and secondary-ref paths).

### Axis B — MySQL NDB Cluster as the closest disaggregated-MySQL analog (cost reporting, pushed joins/SPJ, engine condition pushdown, batched reads)

- NDB hooks the OPPOSITE cost methods from Helios, and that is the central transferable lesson. NDB does NOT override the new Cost_estimate API (read_cost/index_scan_cost/table_scan_cost) that Helios overrides. Instead it (a) IMPLEMENTS the legacy read_time(index,ranges,rows) and (b) OVERRIDES page_read_cost(). The MySQL 8.0 base then COMPUTES read_cost from them: handler::read_cost(index,ranges,rows) = read_time(index,(uint)ranges,(ha_rows)rows) * table->cost_model()->page_read_cost(1.0), then cost.add_io(io_cost) (third_party/mysql-server/sql/handler.cc:6064-6080). So in NDB the per-access-path discrimination lives ENTIRELY in read_time(); page_read_cost is just the scalar multiplier. Helios instead bypasses read_time and writes its own Cost_estimate in helios_ref_cost — which is exactly where the 1024-batch amortization bug lives. NDB's design keeps one authoritative per-row/round-trip formula (read_time) and lets the cost model scale it.
- NDB's read_time() is an explicit PER-INDEX-TYPE fanout model that charges a real round-trip per row for the hostile cases — this is the precise discrimination Helios lacks (ha_ndbcluster.cc:7211-7281). It branches on NDB_INDEX_TYPE: PRIMARY_KEY_INDEX -> fanout_factor = 1.0*rows ('Need a full roundtrip for each row'); UNIQUE_INDEX -> 2.0*rows ('lookup first on UQ, then on PK, + lock/unlock'); ordered/range scan (rows>ranges) -> ranges*(1.0 + fragments_to_scan*0.5) where fragments_to_scan = getPartitionCount() (a partitioned/disaggregated scan fans out to all fragments); single-row PK lookups (rows==ranges) -> ranges*1.0; single-row unique -> ranges*2.0. Final return is fanout_factor + rows2double(rows). The header comment states the intent verbatim: 'fanout_factor is intended to compensate for the amount of roundtrips between API <-> data node and between data nodes themselves by the different index type... we assume a single full roundtrip for each range.' This is the canonical disaggregation cost signal: cost scales with REAL round-trips, and round-trips differ by access method — PK=1, unique=2, ordered-scan fans across fragments.
- NDB's scan_time() = records * 1000 (ha_ndbcluster.cc:7197-7202), 100x larger than Helios's records*10. The comment ties it directly to records_in_range comparability ('to be comparable to the number returned by records_in_range so that we can decide if we should scan the table or use keys'). NDB deliberately makes a full scan look expensive so the optimizer prefers key access WHEN keys are cheap — but NDB then makes per-row key access ALSO expensive via the read_time fanout (1 roundtrip/row). Helios copied the records*10 scan steering but did NOT copy the matching per-row fanout penalty, so in Helios scans look ~expensive while per-row ref looks ~free (amortized /1024) — the worst of both, which is precisely why the optimizer flips to NLJ. The two formulas must be calibrated as a PAIR.
- Pushed joins (AQL/SPJ) are NOT a cost-model competition — they are a post-optimization TRANSFORM applied by a handlerton hook, ndbcluster_push_to_engine(THD*,AccessPath*,JOIN*) registered as hton->push_to_engine (ha_ndbcluster.cc:384, 12684, 14428). The optimizer first picks an ordinary ref/eq_ref nested-loop plan on cost; THEN push_to_engine walks the chosen AccessPath/JOIN and rewrites the NLJ chain into a single SPJ (Select-Project-Join) tree executed inside the data nodes (DBSPJ kernel block). This is the architectural escape hatch from the cost-model trap: instead of fighting the optimizer to avoid NLJ, NDB lets the optimizer choose NLJ and then makes the chosen NLJ cheap by executing it remotely as one pushed operation. handlerton::push_to_engine is an in-tree hook (already used by Helios's allowed surface per MEMORY) and requires NO MySQL-core patch.
- A child table is pushable ONLY if its access type is a lookup (ref/eq_ref/const) or an ordered-index-scan; MRR and anything else is rejected (ha_ndbcluster_push.cc:915-957). Exact gate: ndbcluster_is_mrr_operation(access_type) -> NO_PUSH ('access type not implemented'); then if !(ndbcluster_is_lookup_operation(access_type) || access_type==AT_ORDERED_INDEX_SCAN) -> NO_PUSH ("'type' must be a 'ref' access"). Also limits: no_of_key_fields > MAX_LINKED_KEYS, op count > NDB_SPJ_MAX_TREE_NODES, can't provide rows in index order, join key must be plain columns of EXACTLY the same datatype (ref manual: 't1.a=t2.a+constant' and INT-vs-BIGINT joins are NOT pushable). This tells Helios precisely which join shapes a 'remote join pushdown' could target.
- Engine condition pushdown is the row-reduction lever and ships a 5-10x doc figure plus a measured ~15x transfer reduction. Per MySQL 8.0 manual: 'can eliminate the need to send nonmatching rows over the network between the cluster's data nodes and the MySQL server... and can speed up queries where it is used by a factor of 5 to 10 times.' A community NDB tutorial measured a concrete pushed vs non-pushed join: rows transferred to the API node dropped from 810,981 to 52,793 (~15x less transfer) and time 9.03s -> 5.51s for an identical 50,783-row result. NDB enables it as two switches: optimizer_switch='engine_condition_pushdown' (filter pushdown, default ON) and ndb_join_pushdown (join pushdown). In NDB the condition pushdown is ALSO routed through push_to_engine for non-pushed-join tables, and is SKIPPED for single-row PK/UNIQUE/const access ('It is of limited value to push a condition to a single row access method if not member of a pushed join') (ha_ndbcluster.cc:14450-14478).
- NDB amortizes round-trips with BYTE-budgeted batching, not a fixed row count. ndb_batch_size is a THD var measured in BYTES, default 32768 (ha_ndbcluster.cc:263-271), and NDB implements engine MRR (multi_range_read_info_const / multi_range_read_info, ha_ndbcluster.cc:13311-13466) that coalesces many key lookups into batched scans rather than the default per-row impl. Crucially this means NDB's amortization is a real, bounded buffer (bytes/row determines how many keys actually batch), unlike Helios's helios_ref_cost which divides the RPC by a FIXED kEffBatch=1024 regardless of whether the access path will actually batch. The realistic effective batch = batch_size_bytes / row_bytes, not a constant.
- NDB's records_in_range() returns exactly 1 for a fully-specified unique/PK equality and floors range estimates at 2 (ha_ndbcluster.cc:12861-12912): for HA_NOSAME indexes with both min/max fully specified, equal, and no NULLs -> return 1; partial reads of hash indexes -> HA_POS_ERROR (forces scan); ordered-index ranges use ndb_index_stat_get_rir() but clamp 'if (rows < 2) rows = 2' because 'optimizer thinks values < 2 are exact but we don't provide exact statistics.' This is the same 'cardinality = steering' half Helios already has via NDV/set_records_per_key — and NDB's clamp-to-2 is a deliberate guard against the optimizer over-trusting a '1 row' estimate that would make NLJ look free.

### Axis C — Disaggregated / compute-storage-separated DB cost models (academic + industry): what they change in the optimizer, how Snowflake structurally avoids point-lookup NLJ, and which network-/round-trip-/bytes-aware cost terms are transferable to a MySQL-optimizer-on-remote-store (Helios).

- DOMINANT-COST INVERSION IS THE FOUNDING PREMISE. Aurora's SIGMOD'17 thesis verbatim: 'the constraint... has moved from compute and storage to the network' — the entire architecture is justified by network being the bottleneck. This is the same inversion Helios faces (RPC/bytes dominate, not local IO). The disaggregation survey (Yu, PVLDB vol18 p5527, 2025) quantifies it: 'disaggregation can impose a 10x throughput degradation compared to a highly-optimized shared-nothing database due to excessive network traffic,' so 'an important goal... is to develop optimizations to mitigate the network bottleneck.' Helios's 2x regression is a mild instance of exactly this.
- TWO DISTINCT INDUSTRY STRATEGIES FOR THE OPTIMIZER. (A) OLTP-disaggregation systems (Aurora, Socrates, Taurus, PolarDB) KEEP the engine's local-tuned optimizer essentially UNCHANGED and only offload redo/IO + add pushdown BELOW the engine. Aurora SIGMOD'17: each instance 'supports query processing, access methods, transactions, locking, buffer caching'; only 'redo logging, materialization of data blocks, garbage collection, and backup/restore are offloaded to the storage nodes' — the query optimizer is not re-costed. (B) OLAP-native systems (Snowflake) and HTAP engines (AlloyDB) DO change the cost model / access-path menu to make scan+prune+hash the default and remove the index-NLJ temptation entirely. Helios is the awkward hybrid: an OLTP-tuned optimizer (MySQL) over a remote store running analytics — so it must borrow strategy (B)'s cost discipline while obeying strategy (A)'s 'don't patch the engine' constraint.
- SNOWFLAKE'S ANSWER IS STRUCTURAL, NOT JUST A CONSTANT TWEAK: REMOVE INDEXES FROM THE PLAN SPACE. SIGMOD'16 sec 3.3.1/3.3.2 verbatim: 'Since Snowflake does not use indices... the plan search space is smaller than in some other systems. The plan space is further reduced by postponing many decisions until execution time, for example the type of data distribution for joins. This design reduces the number of bad decisions made by the optimizer, increasing robustness at the cost of a small loss in peak performance.' They explicitly reject B+-tree indices because they rely on 'random access, which is a problem both due to the storage medium (S3) and the data format (compressed files)' — i.e. point lookups are hostile to remote/columnar storage. Their replacement is min-max pruning ('small materialized aggregates / zone maps / data skipping') which 'works well for sequential access of large chunks of data.' DIRECT LESSON FOR HELIOS: the cleanest fix is to shrink the plan space so index-ref-NLJ is not a candidate, rather than to out-cost it after the fact.
- SNOWFLAKE'S OPTIMIZER IS CASCADES TOP-DOWN COST-BASED with auto-maintained stats — so cost-based optimization itself is correct; the failure mode is purely the COST CONSTANTS + plan space, not the framework. The transferable principle: keep cardinality estimation (steering) honest via real stats, but make the COST function value bytes-scanned/round-trips so the only cheap plans are bulk-scan plans. Snowflake never even offers a per-row inner-lookup plan to mis-cost.
- DYNAMIC PRUNING = PREDICATE/SIP TRANSFER IS A FIRST-CLASS SNOWFLAKE TECHNIQUE, exactly matching Helios's q21 win (12.96->4.06s). SIGMOD'16 sec 3.3.2: 'as part of hash join processing, Snowflake collects statistics on the distribution of join keys in the build-side records. This information is then pushed to the probe side and used to filter and possibly skip entire files... in addition to... bloom joins.' PushdownDB (Yu et al., ICDE 2020) generalizes this as 'Bloom join': a Bloom filter built on the small table's keys is sent as an S3 Select predicate so 'rows that do not pass the Bloom filter are not returned.' This is precisely Helios's SIP/predicate-transfer that should be a COST-PREFERRED plan, not just an opportunistic rewrite.
- PUSHDOWNDB GIVES THE EXACT FAILURE CURVE HELIOS IS HITTING, with numbers. ICDE'20 sec IV: per-row index access ('S3-side indexing' = phase 2 sends 'an HTTP request for each individual row') matches bulk S3-side filter ONLY when selectivity < 10^-4; once more rows qualify, 'most of the execution time is spent requesting and receiving individual byte ranges... these requests... incur excessive CPU computation that become a performance bottleneck.' So per-row remote lookups are competitive ONLY at extreme selectivity and degrade catastrophically otherwise — quantitatively justifying Helios charging full un-amortized RPC for non-batched ref-NLJ. Bulk S3-side filter delivers a flat 10x speedup independent of selectivity (the scan+pushdown plan Helios wants).
- TAURUS NDP (Huawei GaussDB-for-MySQL, arXiv:2412/2506) IS THE CLOSEST REAL ANALOG TO HELIOS — a DISAGGREGATED MySQL 8.0 with storage-side processing — and it states the guardrail rule almost verbatim for Helios: 'NDP is only beneficial if an access method reads many rows: for example, a full table scan or range index scan. Accordingly, NDP is not considered for table access methods that access only a few rows—for example, a point lookup.' They gate pushdown with a concrete threshold: 'NDP is enabled on a scan only if the scan is estimated to cause at least 10,000 pages of I/O.' And critically they flag the optimizer-integration trap Helios must avoid: 'a hash-join with NDP pushdown may be better than a nested-loop join without NDP. By not considering NDP during plan enumeration, the optimizer may miss the hash join plan.' Taurus chose post-processing for engineering safety but explicitly acknowledges this means it can MISS the scan+hash plan — so Helios, which CAN influence cost during enumeration via the handler cost hooks, should price scan+pushdown attractively DURING enumeration to capture exactly the plan Taurus leaves on the table.
- ALLOYDB SUPPLIES THE PRODUCTION PATTERN FOR 'COST-BASED ACCESS-PATH CHOICE WITH A TUNABLE THRESHOLD' inside a PostgreSQL planner (analogous to MySQL). It does 'a cost-based hybrid scan in the operator granularity': the planner compares a columnar (bulk) scan vs a row-store index path and 'when the query optimizer detects that a columnar scan would be faster, it automatically uses the columnar data,' but 'an index row scan may be more efficient... depending on the cost.' The decisive transferable knob: google_columnar_engine.scan_cost_threshold — 'higher values mean only larger scans use the columnar engine.' This is the exact lever Helios needs: a single calibrated threshold that tips the cost-based choice toward bulk-scan above a size and toward point access only for tiny/selective accesses — mirroring Taurus's 10k-page gate.
- THE TEXTBOOK DISTRIBUTED-QUERY COST FORMULA VALIDATES HELIOS'S STRUCTURE BUT EXPOSES THE BUG. The classic R*/distributed cost (per multiple distributed-DB references) is communication_time = message_init_cost * (#messages) + per_byte_cost * (#bytes), where inter-site communication dominates. Helios's table_scan = kC_rpc + bytes*kC_byte is exactly one message + bytes (correct). The BUG is that helios_ref_cost amortizes the per-message term over a FIXED kEffBatch=1024 (50/1024 ~= 0.049 per range) regardless of whether the plan actually batches — i.e. it always assumes #messages = #rows/1024 even for a bare per-row ref-NLJ where #messages = #rows. The formula must set #messages to the REAL message count for the access path: 1 (full scan), ceil(rows/batch) (MRR/BKA batched key access), or rows (un-batched per-row ref). That single correction is the load-bearing fix.

### D — OSS distributed/federated optimizers with remote-storage cost factors (TiDB v1/v2, CockroachDB CBO, Apache Calcite, Trino), and the concrete cost-factor design Helios should adopt

- TiDB models the disaggregation boundary with TWO distinct cost dimensions that Helios currently collapses: (1) a per-byte NETWORK cost `rowCount*rowSize*netFactor`, and (2) a per-REQUEST SEEK cost that is FLAT per region/RPC, not per byte. In cost model v1 the defaults are netFactor=1.0 and seekFactor=20.0 (DefOptNetworkFactor=1.0, DefOptSeekFactor=20.0 in pkg/sessionctx/vardef). The seek charge is the single mechanism that makes a per-row index-NLJ expensive: a TableReader/IndexLookUp pays `estimateNetSeekCost` once PER request/range, so a plan that issues one request per outer row accumulates N*seekFactor, while a full scan pays seekFactor once. This is exactly the lever Helios is missing — Helios amortizes its RPC over a FIXED kEffBatch=1024 regardless of actual batching, so a per-row ref-NLJ is mispriced as ~0.049 IO/range.
- TiDB v1 per-operator cost (pkg/planner/core/plan_cost_ver1.go): TableScan/IndexScan self cost = `rowCount*rowSize*scanFactor` (scanFactor=1.5, descScanFactor=3.0 for reverse scans). TableReader/IndexReader cost = `childCost + rowCount*rowSize*netFactor + estimateNetSeekCost(plan)`, then `/ DistSQLScanConcurrency`. IndexLookUp (double read) adds BOTH an index-side network+seek AND a table-side network+seek term — i.e. the cost model explicitly charges the second RPC hop of an index→PK lookup, which is precisely the 'secondary index probe + PK materialize' double cost that Recon-1 flags as missing in Helios's helios_ref_cost.
- TiDB cost model v2 (default since v6.2.0, tidb_cost_model_version=2) re-derives factors by regression calibration to real latency, in pkg/planner/core/plan_cost_ver2.go. Concrete calibrated constants (defaultVer2Factors): TiKVScan=40.70, TiKVDescScan=61.05, TiFlashScan=11.60, TiDBCPU=49.90, TiKVCPU=49.90, TiDB2KVNet=3.96, TiDB2FlashNet=2.20, TiDBMem=0.20, TiDBRequest=6,000,000.00. The huge TiDBRequest=6e6 factor is the v2 successor to seekFactor: each coprocessor task/request costs 6 million units, so issuing many small requests (per-row seeks) is catastrophic versus one bulk scan. v2 scan cost = `rows * max(log2(rowSize),0) * scanFactor` (sublinear in row width via log2), net cost = `rows*rowSize*netFactor`, request cost = `numTasks * requestFactor`.
- TiDB v2 prices index-join seeking as a scan-equivalent, not free: indexJoinSeekingCost = `buildRows * 10 * log2(8) * numRanges * scanFactor` — every build row times every range is charged 10 row-widths of scan, so high-fanout index joins are penalized proportionally to (outer rows × ranges). This answers Recon-1's open question 'should per-row probe cost scale with inner size/fanout' — TiDB's answer is YES, scale by buildRows*numRanges.
- CockroachDB's coster (pkg/sql/opt/xform/coster.go) uses small IO unit costs but a sharp seq-vs-random split that intrinsically favors scans over per-row lookups: cpuCostFactor=0.01, seqIOCostFactor=1, randIOCostFactor=4. A scan charges seqIOCostFactor per row (`rowCount*(seqIOCostFactor+perRowCost)`) plus `numSpans*randIOCostFactor` for span setup. A lookup join charges randIOCostFactor (=4) PER lookup plus lookupJoinRetrieveRowCost(=2) per retrieved row. So lookup is 4x the per-unit IO of a sequential scan row before counting the retrieve, structurally biasing toward scan+hash unless the lookup is very selective.
- CockroachDB makes REMOTE distribution explicitly catastrophic via tiered distribution costs (made the optimizer 'distribution aware', issue #47226): SmallDistributeCost = randIOCostFactor (=4), DistributeCost = 200, LargeDistributeCost = hugeCost (1e100). A plan that must move data across a remote/locality boundary is charged 200, and a disallowed cross-region plan is charged 1e100 — effectively a hard veto via cost, not via a rule. This is the cleanest template for Helios: assign a large flat penalty to any per-row remote operation and a near-infinite penalty to plans that are known-pathological, without patching the optimizer core.
- Trino's cost is a WEIGHTED SUM of three independent dimensions, with network weighted higher than memory (core/trino-main .../OptimizerConfig.java + CostComparator.java): weightedCost = cpuCost*cpuWeight + maxMemory*memoryWeight + networkCost*networkWeight, with defaults cpuCostWeight=75, memoryCostWeight=10, networkCostWeight=15. PlanCostEstimate carries (cpu, maxMemory, network) as SEPARATE accumulators rather than one scalar — the comparator collapses them only at decision time. This is the architecture Helios should mirror: keep per-RPC, per-byte, and per-row CPU as separate Cost_estimate components (MySQL's Cost_estimate already separates io_cost/cpu_cost/mem_cost) and tune their weights.
- Apache Calcite (the pluggable cost framework used by many federated engines) computes cost via RelNode.computeSelfCost() but routes it through RelMetadataQuery.getNonCumulativeCost() so the cost is OVERRIDABLE per-operator/per-adapter without forking the planner. The cost vector is {rowCount, cpu, io}; a custom RelOptCostFactory.makeCost(rows,cpu,io) lets a remote adapter inject network/IO into the io dimension. Critically, the default VolcanoCost.isLe comparison is dominated by rowCount (compares rowCount first), which is a known trap — federated engines MUST supply a custom cost factory that compares on the io/network dimension, or the planner ignores transfer cost. This mirrors Helios's situation: relying on MySQL's default cost constants ignores RPC cost; the fix is to override the cost methods (which Helios already does) AND ensure the dominant term reflects RPC/transfer.
- Academic grounding for the pushdown/predicate-transfer strategy Helios already uses: Predicate Transfer (Yang et al., CIDR 2024) and Robust Predicate Transfer (SIGMOD 2025, implemented in DuckDB) show Bloom-filter pre-filtering across joins cuts multi-join transfer dramatically; 'Including Bloom Filters in Bottom-up Optimization' (arXiv 2505.02994, Huawei Cloud) reports 32.8% latency reduction on TPC-H 100GB by COSTING Bloom filters inside the optimizer. The lesson for Helios's cost model: a plan that ships a filter/Bloom to the remote (SIP/predicate transfer, the q21 win) should be priced as REDUCING downstream remote-row count, so the cost model actively prefers it — cost must be a function of post-filter remote rows, not raw table rows.

### E — Cost-model CALIBRATION methodology & robustness (deriving Helios's cost constants empirically, evaluating cost-vs-cardinality, and guarding against overfitting)

- LEIS ET AL. (PVLDB 2015 / VLDBJ 2018) — THE CORE EVALUATION RESULT, AND ITS CRITICAL NUANCE FOR HELIOS: their headline is 'the cost model has much less influence on query performance than the cardinality estimates' — BUT this holds *because* PostgreSQL's local cost model is already roughly right for a buffer-pool engine. The same paper shows that when cardinalities are accurate, RE-TUNING the cost model still buys ~41% faster runtime (geometric mean over JOB queries). Helios is precisely the regime where cost tuning matters MOST: the recon evidence (39->77s, q7/q18 NLJ flips) is a cost-model defect with cardinality held constant (md5 22/22 identical, OPT_STATS gives real NDV). So Leis does NOT say 'don't bother with the cost model'; it says 'fix cardinality first, then the cost model is the lever' — and Helios has already fixed cardinality (NDV), so the residual is squarely the cost model. Cite Leis as the methodology backbone AND as the justification that Phase-22 is attacking the right component.
- LEIS' SECOND FINDING — A SIMPLE COST MODEL SUFFICES WHEN INPUTS ARE GOOD: 'using true cardinalities, even a simple cost function can fairly accurately predict... and this improvement is dwarfed by the improvement from replacing estimated with real cardinalities.' Implication for Helios: do NOT build an elaborate 8-term cost model. With NDV-backed cardinality, a SMALL number of well-calibrated constants (RPC round-trip cost, per-byte transfer cost, per-row CPU) is enough. The Helios hook already has the right shape (kC_rpc, kC_byte, kC_row); the problem is the VALUES are guessed (50/0.0008/0.10) and one structural term (the /kEffBatch amortization) is wrong, not that the model is too simple.
- WU ET AL. (ICDE 2013) 'Predicting query execution time: Are optimizer cost models really unusable?' IS THE DIRECTLY-TRANSFERABLE CALIBRATION PROTOCOL. They model operator cost as a LINEAR combination of cost units: Cost = c_t·n_t + c_o·n_o + c_s·n_s + c_i·n_i + c_r·n_r, where n_* are operator-emitted COUNTS (tuples processed, operator invocations, sequential pages, index tuples, random pages) and c_* are the per-unit costs to be calibrated. They design ONE isolation micro-query per cost unit, run it with the relevant data forced into/out of cache, measure wall-clock time, build a count matrix N whose rows are the per-query operator counts (chosen so det(N)!=0), and SOLVE N·c = t by least-squares regression for the constant vector c. Reported: profiling takes <1 hour, and a *calibrated* white-box cost model predicts runtime better than black-box ML. THIS IS THE EXACT RECIPE Helios needs, with Helios's unit set substituted.
- WU'S ISOLATION-QUERY DESIGN (the part to copy verbatim, retargeted to Helios): cpu_tuple_cost from `SELECT * FROM R` with R fully buffered (only per-tuple CPU varies); cpu_operator_cost from `SELECT COUNT(*) FROM R` buffered (adds one operator eval per row over the previous); seq_page_cost from `SELECT * FROM R` forced to a cold sequential scan (now page I/O dominates); random_page_cost from `SELECT * FROM R WHERE R.B<b` via an UNCLUSTERED index (random-page I/O). Each query is constructed so that exactly one new cost term becomes the dominant unknown, making the linear system well-conditioned. Helios's analogue: scan-1-RPC query, point-lookup-1-RPC query, B-key batched-MRR query, hash-build/probe query — each isolating one of {C_rpc, C_byte/transfer, C_row, batch effect}.

- ADAPTIVE COST MODEL (ACM, Vasilenko et al., arXiv 2409.17136, 2024) GIVES THE MECHANISM FOR THE EXACT HELIOS BUG. ACM observes that the static seq/random page split mis-estimates because the optimizer doesn't know what's already in cache; it dynamically recomputes per-table random_page_cost from a measured hit ratio R(q)=hit/(hit+read), interpolating random_page_cost toward seq_page_cost as more of the table is cached (20% TPC-H latency win). The Helios parallel is structural, not about cache: the RIGHT 'effective batch' for a ref lookup is NOT a static 1024 — it depends on whether the chosen access path will actually coalesce probes (MRR/BKA) or issue one RPC per outer row. ACM's lesson: make the contested constant a measured/conditional quantity, not a fixed scalar. For Helios that means kEffBatch must be ~1 for a bare per-row REF path and ~B for an MRR/BKA-batched path.
- THE STRUCTURAL ROOT-CAUSE THE CALIBRATION MUST FIX (confirmed against the hook source): helios_ref_cost charges RPC as ranges·(kC_rpc/kEffBatch) with kEffBatch=1024, i.e. ~0.049 IO per range, UNCONDITIONALLY assuming 1024-way batching even when the plan does per-outer-row lookups. No achievable calibration of the SCALAR kC_rpc fixes this: lower it and scans are mispriced; raise it and you re-introduce the q10/q3 over-penalty the worklog already hit. The fit must instead make the RPC charge PER-ACCESS-PATH (un-amortized for non-batched REF). This is the Leis/Wu 'use the right cost-unit decomposition' principle applied to disaggregation.
- OBSERVABILITY CONSTRAINT THAT BOUNDS THE PROTOCOL (Helios-specific, from worklog: REF/EQ_REF/MRR AccessPath struct carries no distinguishing field — access_path.h:870-876): at the moment read_cost()/index_scan_cost() is called, the handler may NOT be told whether the join executor will batch this index access via MRR/BKA. The calibration protocol must therefore be run TWICE — once with MRR advertised, once without — and the constants chosen so the optimizer cannot pick a cheap-priced per-row REF.
- LEARNED COST/CARDINALITY MODELS (Bao SIGMOD 2021; Flow-Loss PVLDB 2021) ARE THE NOTED ALTERNATIVE BUT NOT THE RECOMMENDATION FOR PHASE-22. Flow-Loss shows that what matters is estimates/costs that change the CHOSEN PLAN, not minimizing Q-error — directly relevant: Helios should calibrate to flip the q7/q18 plan decisions, not to minimize global cost prediction error. ### Axis F — In-memory / columnar / pushdown engines: costing away from the IO-block model (DuckDB, HeatWave/RAPID, Oracle 12c In-Memory, Spark Catalyst CBO, Presto/Velox, main-memory hash-join cost models)

- LINEAR DISK-IO COST IS THE WRONG ABSTRACTION FOR MEMORY — REPLACE IT WITH A WEIGHTED ACCESS-PATTERN MODEL. Liu & Blanas (VLDB 2015, 'Forecasting the cost of processing multi-join queries via hashing for main-memory databases') show PostgreSQL's linear model Cost(Q) = n_s*c_s + n_r*c_r (sequential count * seq cost + random count * random cost) mispredicts in-memory hash-join runtime by up to 2x. They replace it with Time(Q) ∝ w_SR*N(SR) + w_RR*N(RR) + w_SW*N(SW) + w_RW*N(RW): four memory access patterns (sequential/random x read/write), each weighted by an EMPIRICALLY MEASURED per-access cost w_A (microbenchmarked per machine, their Table 3 spans Intel/AMD/EC2). The transferable principle for Helios: the cost basis should be 'count of each KIND of remote access x measured cost of that kind', not page IO. For Helios the dominant 'random access' pattern is the per-row RPC; the 'sequential' pattern is the bulk scan/prefetch — these must carry DIFFERENT, separately-calibrated weights, exactly as SR vs RR differ in their model.
- THE NLJ-vs-SCAN PROBLEM IS THE SAME 'RANDOM-ACCESS COUNTING' PROBLEM. Liu & Blanas Insight 2 quantifies why per-row (random) access dominates: a left-deep plan performs n*|R_n| - Σ|R_i| FEWER random-read memory accesses than right-deep, and that random-access count is what blows up cost by ~10x as the join chain lengthens. The lesson directly maps: an index-NLJ issues |outer| RANDOM remote probes (one RPC per outer row), while scan+hash issues O(1) SEQUENTIAL bulk fetches. A correct Helios cost model must count random remote accesses explicitly and weight them at the TRUE un-amortized RPC cost — Helios's current bug is that helios_ref_cost amortizes every ref probe over a fixed batch of 1024 (rpc = ranges*(kC_rpc/1024)), i.e. it prices a per-row random RPC as if it were sequential/batched, collapsing the very RR-vs-SR distinction the literature says is the whole point.
- PURE-CARDINALITY COST MODELS DELIBERATELY MAKE SCAN+HASH WIN AND STRUCTURALLY CANNOT PICK PER-ROW NLJ. DuckDB's join-order cost (src/optimizer/join_order/cost_model.cpp, ComputeCost) is literally cost = join_cardinality + left.cost + right.cost — NO per-tuple CPU term, NO IO term, NO index-lookup discount. Cardinality is estimated FK-PK style as |t1 ⋈ t2| ≈ (|t1|*|t2|)/max(domain(t1.A),domain(t2.A)) using HyperLogLog NDV. Because cost = sum of intermediate cardinalities, a plan that pushes selective filters early and uses hash joins always dominates; there is no cost path that rewards a per-row index probe. DuckDB has essentially no per-row-lookup index-NLJ plan to flip into. This is the cleanest existence proof that an in-memory engine should drive plan choice off INTERMEDIATE CARDINALITY (transfer volume), letting hash join be the default physical operator, and reserve index/point access only for genuinely tiny selective lookups.
- SPARK CATALYST CBO GIVES A CLEAN TWO-TERM TRANSFERABLE FORMULA + A HARD SIZE GATE. Spark CBO ranks join orders by cost = card * w + size * (1-w) where w = spark.sql.cbo.joinReorder.card.weight (default 0.7) — i.e. 70% weight on ROW COUNT, 30% on BYTE SIZE (CostBasedJoinReorder; cf. SPARK-33935 which fixed the relative-vs-absolute form to card*w + size*(1-w)). Separately, physical join selection is gated by a HARD SIZE THRESHOLD: spark.sql.autoBroadcastJoinThreshold (default 10MB) — if a build side fits under it, broadcast-hash-join (build once in memory, probe locally, NO per-row shuffle) is chosen over shuffle/sort-merge. The two ideas transfer: (a) Helios cost should be a weighted blend of rows-transferred and bytes-transferred (it already has both terms but mis-weights the RPC component); (b) a HARD threshold can force the helios-friendly operator (full-scan+hash / batched-key) when a relation is small, bypassing cardinality-estimate fragility entirely.
- ORACLE 12c IN-MEMORY IS THE CLOSEST ANALOG: A SELECTIVITY-CROSSOVER COST MODEL THAT FLIPS SCAN-vs-INDEX BY DATA SHAPE, NOT BY A PAGE-IO MODEL. Das et al. (VLDB 2015, 'Query Optimization in Oracle 12c Database In-Memory') and patent US10073885 add NEW in-memory scan cost components on top of the legacy cost units: (1) in-memory quotient (fraction resident), (2) #IMCUs to scan AFTER storage-index min/max pruning, (3) decompression cost (per compression method), (4) predicate-evaluation cost (pushed-down predicates evaluated during scan), (5) row-stitching cost, (6) transaction-journal scan cost. The DECISION RULE Oracle states explicitly: 'looking up a SMALL NUMBER OF ROWS with an index on the WHERE column -> index access (lowest cost); accessing a SMALL NUMBER OF COLUMNS from a LARGE NUMBER OF ROWS -> in-memory full scan.' So the scan-vs-index crossover is governed by SELECTIVITY (rows touched) and PROJECTION WIDTH (columns), with the in-memory scan made cheap precisely because predicate+projection pushdown shrink what is scanned. For Helios this prescribes: cost the full-scan+pushdown path with a per-row cost LOW ENOUGH that it beats index-NLJ except for genuinely point-selective lookups, and let projection/predicate pushdown (which Helios already has) REDUCE the costed bytes so scan dominates.
- HEATWAVE (RAPID) OFFLOAD = COMPARE TWO ENGINE COST ESTIMATES, NOT A SINGLE NLJ DISCOUNT — A USEFUL MODEL FOR 'PREFER THE PUSHDOWN ENGINE.' MySQL decides to offload to HeatWave when (a) every operator/function is supported by RAPID AND (b) the ESTIMATED HeatWave execution time < estimated InnoDB execution time. The legacy gate (pre-MySQL 9.0) was secondary_engine_cost_threshold (default 100000.0): a query whose PRIMARY-engine cost exceeds the threshold is CONSIDERED for the secondary engine. As of MySQL 9.0 this became 'dynamic query offload' which weighs query characteristics, engine static+dynamic characteristics, current RAPID queue depth, and 'presence of indexes on the primary engine.' Two transferable ideas: (1) the offload model is a TWO-ESTIMATE COMPARISON (in-memory/pushdown plan cost vs row-engine plan cost), which is exactly the scan+pushdown-vs-NLJ comparison Helios must win; (2) a COST THRESHOLD that routes only 'big enough' (analytic) queries to the scan/pushdown path mirrors Helios wanting OLTP point queries to stay on cheap single-key access while analytic scans go full-scan+hash — and notably HeatWave EXPLICITLY accounts for 'presence of indexes on InnoDB' as a factor, i.e. index presence should not silently re-price the analytic plan, which is precisely Helios's 39->77s regression.
- ROBUSTNESS-FIRST DESIGN BEATS ESTIMATE-PERFECTING: PRE-FILTER (PREDICATE TRANSFER) MAKES JOIN-ORDER/COST CHOICE ALMOST IRRELEVANT. 'Debunking the Myth of Join Ordering: Toward Robust SQL Analytics' (arXiv 2502.15181) shows Robust Predicate Transfer (RPT) — Bloom-filter semi-join reduction (extending Yannakakis) applied BEFORE the join phase — cuts the robustness factor (slowest/fastest plan ratio) from ~30x to ~1.2x for acyclic queries (94% of the benchmark). The mechanism: aggressively eliminate non-joining tuples up front so intermediate results are bounded REGARDLESS of join order, after which plain hash joins finish the work. This is the SAME family as Helios's already-shipped SharedScan / SIP / semijoin-reduction (q21 12.96->4.06s). The cost-model takeaway: rather than chasing a perfectly calibrated NLJ price, make the cost model PREFER plans that ship a reducer/filter to the server first (pushdown + hash), so that even imperfect cardinality estimates cannot tip the plan into a catastrophic per-row NLJ. Cost = guardrail; predicate-transfer = the safety net.
- PRESTO HISTORY-BASED OPTIMIZATION (HBO) + ADAPTIVE COST MODELS: CALIBRATE COST FROM MEASURED RUNTIME, NOT STATIC CONSTANTS. Presto's HBO (prestodb.io blog, 2024; VLDB vol17 p4077) records ACTUAL execution stats (output rows, CPU, memory, NETWORK usage) per plan node into a store (Redis), maps future plan nodes to their 'stats-equivalent' historical node, and folds real measurements into the cost vector (a vector of metrics reduced to a weighted scalar; weights adapt to whether the query is compute- vs memory-heavy). Its canonical fix is exactly Helios's failure mode: a heuristic estimate of 150 rows vs actual 2.8 billion led to a bad build side / non-broadcast join; HBO's measured cardinality corrected it to a broadcast (in-memory) join. The 'Adaptive Cost Model' paper (arXiv 2409.17136) similarly tunes CPU/IO cost parameters at runtime from execution stats for ~20% TPC-H latency gains. Transferable: Helios's kC_rpc / kC_byte / kC_row / kC_probe should not be hand-guessed env vars — they should be CALIBRATED from measured per-RPC latency and per-byte transfer time on the actual disaggregation link (microbenchmark the link like Liu & Blanas microbenchmark the memory bus), and ideally refined from observed query runtimes.

### codex: calibration protocol

- The existing ENABLE_RPC_TRACE JSONL surface is sufficient to calibrate the network-dominant cost model WITHOUT any MySQL-core change. Set env ENABLE_RPC_TRACE=1 on mysqld (proxy/rpc_trace.cc:351) -> writes /tmp/helios_rpc_trace_PID.jsonl (override via ENABLE_RPC_TRACE_PATH). Each per-tx record (proxy/rpc_trace.cc:230-300) carries duration_us, rpc_count, stmt_count, statements[]{sql,started_off_us,first/last_rpc}, and rpcs[]{type,off_us,us,req_b,resp_b,stmt,meta} plus section timers (stage_rpc_and_decode, stage_local, staged_rows, plan_steps_covered, abort_* reasons).
- rpcs[].type is a MessageType name (proxy/rpc_trace.cc:30) and is the per-primitive attribution key: TX_READ (point read), TX_READ_SECONDARY_INDEX, TX_GET_MATCHING_KEYS_AND_VALUES_IN_RANGE (range scan w/ values), TX_GET_MATCHING_PRIMARY_KEYS_IN_RANGE, TX_FETCH_*_KEY_*, TX_EXECUTE_READ_PLAN (single prefetch plan RPC). bench/bin/rpc_trace_agg.py aggregates RPC time + bytes BY message type and computes residual = duration - rpc - sections (MySQL executor + proxy CPU).
- The under-pricing target is precisely isolated: helios_ref_cost() (proxy/ha_lineairdb.hh:348) charges io=(ranges>0?ranges:1)*(kC_rpc/kEffBatch) with FIXED kEffBatch=1024, so a per-outer-row ref/eq_ref NLJ that actually emits one TX_READ per row is priced as if always 1024-batched. Calibration must classify each key-access path by measured RPCs-per-key (B_eff = logical_keys / actual_key_access_RPCs) and refuse the kEffBatch amortization when B_eff ~= 1.
- The full harness already exists and is reusable: build (scripts/build_partial.sh), start (scripts/start_server.sh, scripts/start_mysql.sh with gates HELIOS_OPT_STATS=1 HELIOS_COST_V2=1 HELIOS_AGG_PUSHDOWN=1 HELIOS_ENABLE_SEMIJOIN=1), latency (bench/bin/tpch_matrix.sh), md5 correctness (bench/bin/tpch_md5.sh, scripts/dev/afterload_selfcheck.sh), plan shape (bench/bin/tpch_explain_diff.sh, EXPLAIN FORMAT=TREE), 3-way perf (scripts/dev/perf_sf1_afterload.sh), OLTP non-regression (scripts/dev/oltp_regression.sh, scripts/dev/tpcc_compare.sh).
- Mandatory environment invariants per measurement: prefetch is a GLOBAL sysvar (lineairdb_prefetch_execution / lineairdb_prefetch_ro_novalidate, proxy/ha_lineairdb.cc:4512) that RESETS to OFF on every mysqld restart and must be re-SET; the LineairDB server is IN-MEMORY so any restart wipes data (reload required); NDV must be prewarmed once per mysqld lifetime (scripts/dev/prewarm_stats.sh) so the one-time TX_GET_TABLE_STATS does not contaminate measured queries; host must be cstate-pinned (scripts/dev/cstate_guard.sh) because C6 deep-sleep throttled TPC-C T1 ~3.7x.
- POSSIBLE GAP: C_row (local row evaluation) vs C_remote (remote materialization) cannot necessarily be separated from the existing generic section timers. The trace exposes only the sums the model actually uses (scan row slope = C_row+C_remote; ref row slope = C_probe+C_row). If a true split is required, the minimal addition is a trace counter that separately times remote row materialization vs local row evaluation; otherwise fit only the sums.
